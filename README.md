# ATLAS AI

**Multi-Agent Investment Intelligence Platform** — a hackathon prototype that analyzes
US equities with specialized analyzers and a supervisor, producing an explainable,
auditable result.

> **Current status: Phase 2 (analytical engine on a demo dataset).**
> All prices and fundamentals are **SYNTHETIC demo data**. They are not real market
> data. The app is an educational prototype. It is **not investment advice** and it
> does not guarantee returns. No brokers, real money or live data are used.

## Architecture

```
frontend/  Next.js + TypeScript + Tailwind  ──POST /api/analyze──▶  backend/  FastAPI
(UI: input, states, analyzer panels)                                (API layer → service → engine → data)
```

Backend layers, each with one responsibility:

```
app/main.py            HTTP routes, CORS, error mapping only. No financial logic.
app/schemas.py         Pydantic models = the API contract.
app/analysis/          Deterministic analysis engine (no I/O).
  service.py           Orchestrates: provider → analyzers → aggregator → response.
  technical.py         Momentum and trend.
  risk.py              Volatility, max drawdown, risk label.
  fundamental.py       Demo fundamentals → score.
  aggregate.py         Weighted composite → BUY / HOLD / SELL, confidence.
  indicators.py        Pure functions (period change, SMA, volatility, drawdown).
  narrative.py         Template-based explanations. No LLM; numbers come from results.
  config.py            Every window, weight, threshold and scale, in one place.
app/data/              Market data layer.
  provider.py          Abstract MarketDataProvider interface (swap in a real one later).
  demo_provider.py     Serves the bundled demo dataset. Works offline.
  demo_dataset.json    Static synthetic dataset (see "Demo dataset" below).
  validation.py        Detects bad bars (non-positive price, inconsistent OHLC, dates).
```

Analysis code depends only on the `MarketDataProvider` interface. A real provider can
replace `DemoDataProvider` in `app/main.py` without changing the analysis or the API.

## Demo dataset

- **File:** `backend/app/data/demo_dataset.json` (7 symbols × 120 business days).
- **Symbols:** AAPL, MSFT, NVDA, TSLA, AMZN, GOOGL, META.
- **Fields per bar:** date, open, high, low, close, volume.
- **Dates:** 2026-04-16 → 2026-09-30 (business days; exchange holidays ignored).
- **Origin:** generated by `backend/scripts/generate_demo_dataset.py`. Prices come from
  a geometric random walk seeded per symbol (`atlas-ai-demo-v1-<SYMBOL>`), so the file
  is identical on every run. The drift, volatility and starting prices are illustrative
  parameters chosen for the demo. They do not describe any real company.
- **Fundamentals:** hand-written demo values, not reported financials.
- **Regenerate** (optional, produces the identical file):

  ```bash
  cd backend && ./.venv/bin/python scripts/generate_demo_dataset.py
  ```

## Formulas

Every formula is implemented in `backend/app/analysis/` and every constant lives in
`config.py`. These are educational rules, not calibrated predictions.

**Momentum** (`technical.py`)
- `changePercent = (last close / first close − 1) × 100`
- `score = clamp(period change / 0.20, −1, 1)`
- Label: `positive` if score ≥ 0.20, `negative` if ≤ −0.20, else `neutral`.

**Trend** (`technical.py`) — needs at least 50 closes.
- `SMA20` and `SMA50` are the means of the last 20 and 50 closes.
- `gap₁ = SMA20 / SMA50 − 1`, `gap₂ = price / SMA20 − 1`, each clamped to ±1 after dividing by 0.10.
- `score = (gap₁ + gap₂) / 2`
- Label: `bullish` / `neutral` / `bearish` using the same ±0.20 band.

**Risk** (`risk.py`) — educational only. Describes past behaviour; does not predict it.
- `volatility = std(daily log returns, ddof=1) × √252` (annualized).
- `maxDrawdown = −min(close / running peak − 1)`, reported as a positive magnitude.
- `riskScore = min(1, 0.6 × volatility / 0.60 + 0.4 × maxDrawdown / 0.50)`
- Label: `low` if < 0.33, `moderate` if < 0.66, otherwise `high`.
- Signal passed to the aggregator: `1 − 2 × riskScore` (low risk is favorable).

**Fundamentals** (`fundamental.py`) — demo metrics only.
- Each available metric maps linearly to [−1, 1]: its "bad" value → −1, its "good" value → +1, clamped.
  - Revenue growth: bad 0%, good 10%.
  - Profit margin: bad 5%, good 20%.
  - P/E ratio: bad 45, good 25 (reversed: lower is better).
  - Earnings growth: bad 0%, good 10%.
- `score` = mean of the available metric scores.
- A **missing metric is excluded**. It is never treated as a positive or negative signal.

**Aggregation** (`aggregate.py`)
- Weights: momentum 30%, trend 30%, risk 20%, fundamentals 20%.
- `composite = Σ(wᵢ·sᵢ) / Σwᵢ` over **available** components only (weights renormalized).
- `recommendation`: `BUY` if composite ≥ +0.25, `SELL` if ≤ −0.25, otherwise `HOLD`.
- Unavailable components are reported in `explanation` and excluded.

**Confidence** (`aggregate.py`)
- `coverage = Σwᵢ(available) / Σwᵢ(all)`
- `agreement = 1 − min(1, population std dev of available scores)`
- `confidence = coverage × agreement`, rounded to 2 decimals.
- This measures **data completeness and signal consistency**. It is **not** the probability
  that the recommendation is correct.

## Running locally

```bash
# Backend
cd backend
python3 -m venv .venv
./.venv/bin/pip install -r requirements.txt
./.venv/bin/uvicorn app.main:app --port 8000

# Frontend (second terminal)
cd frontend
npm install
npm run dev          # development, http://localhost:3000
# or: npm run build && npm start
```

Open http://localhost:3000 and try `NVDA`, `TSLA`, `AAPL`, `MSFT`, `AMZN`, `GOOGL` or `META`.
Invalid format returns 400. Unknown symbols return 404. Both show a clear error.

Configuration (optional): `backend/.env.example` → `ATLAS_CORS_ORIGINS`, the Phase 4
narration settings and the Phase 5 paper trading settings; `frontend/.env.example` →
`NEXT_PUBLIC_API_URL`. No credentials are required unless you enable paper trading. The backend does not load `.env` by itself: export the variables (or
`set -a; source .env; set +a`) in the shell that starts uvicorn.

## Tests

```bash
cd backend && ./.venv/bin/python -m pytest -q
```

The suite covers: the dataset (presence, OHLCV fields, ordering, determinism, validation),
indicator formulas against hand-computed values, each analyzer (including a high-volatility
scenario, insufficient history and missing fundamentals), the aggregator (BUY / HOLD / SELL,
renormalization, confidence), the service contract, and the HTTP API (valid, normalized,
malformed, unknown and invalid-body requests). Phase 3 adds supervisor tests for each rule,
exact thresholds, status precedence, data quality and provenance, report wording, and the
HTTP supervision contract for all seven demo symbols. Phase 4 adds narration tests with a
mocked HTTP transport (no LM Studio needed): configuration, evidence packet, output validation,
fallback in both languages, connection/timeout/HTTP/malformed/busy cases and the
`/api/report` contract. Phase 5 adds paper trading tests with a fake broker and a mocked
HTTP transport (no test calls Alpaca): configuration guards, validation rules, idempotent and
concurrent confirmation, uncertain submissions, reconciliation, restart recovery, fills,
cancellation and the `/api/paper` contract. Phase 5.5 adds reservation tests across proposals
(concurrency, stale snapshots, double counting, fills, migration, leases).


## Limitations

- **All data is synthetic.** Results describe the demo dataset, not any real company.
- Only 7 demo symbols are available. There is no live or historical market data source yet.
- Fundamentals are hand-written demo values. They are not verified financials.
- Thresholds, weights and scales are educational choices. They are not backtested or calibrated.
- Confidence measures data coverage and agreement between signals. It is not a probability.
- Exchange holidays are ignored in the demo calendar.
- The UI was verified by typecheck, lint and production build, and the API it consumes was
  verified live over HTTP. Interactive browser testing was not possible in this environment
  (the sandbox blocks browser downloads), so manual UI testing is still recommended.

## Supervisor (Phase 3)

`POST /api/analyze` now includes a `supervision` block. It is produced by deterministic
rules that read the finished analysis. The supervisor does not query data or recompute
indicators, and it works offline with no LLM.

- **Status:** `insufficient_data` > `caution` > `consistent` (precedence in that order).
- **Findings:** contradictions (`MOMENTUM_TREND_DIVERGENCE`, `TECHNICAL_FUNDAMENTAL_DIVERGENCE`),
  a caution (`OPPORTUNITY_RISK_CONFLICT`), data gaps (`HISTORY_INSUFFICIENT`,
  `FUNDAMENTALS_MISSING`, `FUNDAMENTALS_PARTIAL`) and an observation (`LOW_CONFIDENCE`).
- **Thresholds:** direction threshold 0.20 (inclusive); low confidence below 0.50.
  All values are in `backend/app/supervision/config.py`.
- **Evidence (policy `phase3-v2`, schema `1.1`):** each signal has a `polarity`
  (favorable / unfavorable / neutral) and a `direction` relative to the recommendation
  (`supportingEvidence`, `opposingEvidence`, `neutralEvidence`). For a SELL, unfavorable
  signals are the supporting reasons. Risk is a direction only for BUY; for HOLD and SELL it
  is neutral context, and high risk always appears in `riskFactors`.
- **References:** every ref resolves in the final HTTP JSON (for example
  `analysis.trend.shortMovingAverage`, `supervision.dataQuality.historicalObservations`).
  An unresolved ref is an integrity error (HTTP 500).
- **Report:** `headline`, `summary`, `keyReasons` (why the recommendation), `counterpoints`
  (against it), `riskFactors`, `dataGaps`, built from fixed templates. Provenance wording is
  derived from `dataQuality.provenance`. The output is deterministic.

Full rules, the evidence policy, status definitions, the confidence meaning, frontend
guidance and real synthetic examples (NVDA, TSLA, a HOLD and an insufficient-history case)
are in [docs/phase-3-supervisor.md](docs/phase-3-supervisor.md).

## Narrative report (Phase 4)

`POST /api/report` returns the analysis plus a narrative in `es` (default) or `en`. When
`ATLAS_NARRATION_ENABLED=true`, the narrative is written by a model served locally by
LM Studio (for example Gemma), at the configured `ATLAS_LM_STUDIO_MODEL`. The backend
validates the output: strict schema, existing evidence IDs, every supervisor item cited in
the right section, no digits, no banned phrases, the engine's recommendation only, the
requested language. Otherwise, or on any model failure (unavailable, timeout, busy, invalid
output), it returns a deterministic report built from the supervisor, with a reason code.
The recommendation, confidence, metrics and status always come from the deterministic
backend. `/api/analyze` never calls the model.

Setup, the full contract, validation limits, frontend guidance and the manual LM Studio check
are in [docs/phase-4-narration.md](docs/phase-4-narration.md). The check against a real
model has not been run yet.

## Paper Trading Lab (Phase 5)

Optional and off by default (`ATLAS_PAPER_TRADING_ENABLED=false`). With paper credentials, the
backend prepares, validates, confirms and tracks **simulated** market orders in an
**Alpaca Paper** account. The endpoint is fixed to `https://paper-api.alpaca.markets`; any live
configuration stops the server. Buys are by USD notional, sells by quantity of an existing
long position, during the regular session, with no shorts, leverage, options or crypto.

Preparing a proposal never submits. Confirmation requires
`{"confirmation": "CONFIRM_PAPER_ORDER"}` and submits at most once per proposal. A database
transaction plus a unique `client_order_id` enforce this. An uncertain result
(`submission_unknown`) is reconciled by `client_order_id` and never resent. Analysis and
narrative never create or confirm orders, and the synthetic analysis is never used for prices.

**Phase 5.5 (reservations):** confirming a proposal reserves its cash or shares in SQLite in the
same transaction that marks it as submitting, after re-checking capacity against every other
active reservation. Two proposals can no longer commit the same shares or budget. An uncertain
submission keeps its reservation until Alpaca reports the order as final. Capacity uses
`min(broker figure, figure recomputed from the open-order list)` so stale snapshots cannot
over-commit and acknowledged orders are not counted twice. New codes: `RESOURCE_RESERVED` and
`RECONCILIATION_REQUIRED` (409). Existing Phase 5 databases are migrated in place.

**Phase 5.6 (executed consumption):** ATLAS keeps a local ledger of its own fills (cash and shares
per symbol) from a trusted checkpoint, and caps availability at `min(snapshot, ledger)`. A fill that
Alpaca's account or position snapshot does not show yet stays protected, and a fresh snapshot is not
counted twice. Alpaca exposes no snapshot timestamps or versions, so when an operation fits the
snapshot but not the ledger, the answer is `RECONCILIATION_REQUIRED` until the broker catches up.
Order observations are monotonic. Pre-5.6 local data is marked unverifiable. See
`docs/phase-5-paper-trading.md` → "Phase 5.6".

The backend has no authentication: run it locally only. Contract, states, errors, frontend
guidance and the manual check are in [docs/phase-5-paper-trading.md](docs/phase-5-paper-trading.md).
The check against a real Alpaca Paper account has not been run yet.
